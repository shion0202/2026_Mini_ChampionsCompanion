# 구축기사 수집 자동화 설계

`docs/articles.md`의 등록 기준은 그대로 두고, 그 기준을 만족하는 후보를 모아
사람 앞에 압축해 내놓는 도구를 만든다. 판정과 공개 결정은 여전히 사람 몫이다.

원문 전문을 AI 컨텍스트에 넣지 않는 것이 이 설계의 목적이다. 이름 읽기와 근거
수집은 로컬 데이터로 결정론적으로 처리하고, 비용을 쓸 가치가 있는 판단
— 이 여섯 마리가 **최종** 파티인가 — 에만 AI를 한 번 쓴다.

## 단계

| 단계 | 수행 주체 | 산출물 |
| --- | --- | --- |
| 1 수집 | `scripts/collect-articles.mjs` | `.cache/articles/<sha1>.html`, 이미지 |
| 2 추출 | `scripts/article-parse.mjs` | `.cache/article-queue.json` (기사당 약 2KB) |
| 3 판정 | Claude Code 세션 | 최종 6마리와 근거문을 `pending`으로 기록 |
| 4 승격 | 사람 | `articles.json`의 `pending` → `reviewed` |

## 사전 측정

설계 중 실제 기사와 검색 피드로 다음을 확인했다. 숫자는 추정이 아니라 측정값이다.

- 하테나 북마크 검색 RSS 한 번에 40건이 돌아오고 그중 22건의 제목에 최종 순위가
  있었다. 나머지는 뉴스, 공략 사이트, 무관한 글이며 2단계 필터가 걸러낼 종류다.
- 그 40건에는 note, pokesol, fc2, seesaa, 개인 도메인 기사가 모두 섞여 있었다.
  **소스별 어댑터를 따로 만들 필요가 없다.**
- 기존 기록인 rebo 기사(`reboiona.hatenablog.com`)를 파싱하니 최종 6마리가 모두
  후보에 잡혔고 점수 상위 12위 안에 5마리가 들었다.
- 같은 기사에서 **도구는 6개 중 4개만 본문에 있었다.** 메가스톤 둘과
  `こだわりスカーフ`는 본문에 없고 작성자의 팀 이미지에만 있었다.
- 그 기사는 개별 해설에 `h2`/`h3`를 쓰지 않았다. **헤딩은 신뢰할 신호가 아니다.**

마지막 두 항목이 설계를 바꿨다. 텍스트만으로는 파티가 완성되지 않는다. 이미지가
판정의 중심이고, 압축 표는 이미지를 읽을 때 쓰는 대조표 역할을 한다.

## 1단계 · 수집

`npm run articles -- --season M5 --format singles`

`--season`은 필수다. `--format`을 생략하면 싱글과 더블을 모두 찾는다.

### 검색어

게임명 상수 네 개를 순위 표현과 조합한다.

- `ポケモンチャンピオンズ`
- `ポケモン チャンピオンズ`
- `ポケチャン`
- `チャンピオンズ`

앞의 두 개는 공백만 다르다. 하테나는 공백을 AND 검색으로 쪼개므로, 형태소
분석기가 복합어를 알아서 나누면 결과가 같고 아니면 다르다. 확인하는 비용보다
둘 다 넣는 비용이 싸다. URL 중복 제거가 겹치는 결과를 걷어낸다.

마지막 것은 포켓몬 외 결과가 섞일 수 있으나, 2단계의 챔피언스 종족 필터와 제목
순위 파싱이 걸러낸다. 순위 표현은 `最終`, 형식은 `シングル` / `ダブル`, 시즌은
`--season` 인자를 `M-5` / `S5` 두 표기로 펼쳐 붙인다.

### 소스

하테나 북마크 검색 RSS 하나로 시작한다.

```
https://b.hatena.ne.jp/q/<검색어>?mode=rss&target=text&users=1&sort=recent
```

`users` 기본값이 3이라 그대로 두면 북마크 3개 미만인 개인 구축기사가 거의 전부
빠진다. 측정에서 40건과 4건으로 갈렸으므로 `users=1`을 반드시 붙인다.
`/search/text` 경로는 이 주소로 301 이동한다.

X(트위터)는 무료 경로가 없어 제외한다. 하테나가 못 잡는 소스가 확인되면 그때
어댑터를 `{ name, searchUrl(query), links(body) }` 형태로 추가한다. 지금 미리
만들지 않는다.

### 요청 규칙

원문은 `.cache/articles/<sha1>.html`에 캐시하고 캐시가 있으면 다시 받지 않는다.
요청 간 1초 간격을 두고 User-Agent에 이 저장소를 밝힌다. `articles.json`에 이미
있는 URL은 건너뛴다. `.cache/`는 gitignore이므로 원문 텍스트와 이미지는 커밋에
들어가지 않는다. 커밋되는 것은 추출된 사실뿐이다.

## 2단계 · 추출

`scripts/article-parse.mjs`는 네트워크를 쓰지 않는 순수 함수만 내보낸다.
고정 픽스처로 테스트하고, 파서를 고칠 때 원문을 다시 긁지 않기 위해서다.

### 일본어 인덱스

`reference.json`과 `ko.json`에서 빌드한다.

- 기본 종족 1024건 — `ko.json`의 `japanese.pokemon`
- 메가 폼 — `メガ` + 기본명 + `forme`의 꼬리(`X` / `Y` / `Z`).
  `species.megas`에 있는 폼만 만든다.
- 리전 폼 — `アローラ` / `ガラル` / `ヒスイ` / `パルデア` + 기본명
- 도구 431건 — `reference.json`의 `held_item[].japanese`
- 도구 약칭 — `スカーフ`, `タスキ`, `ゴツメ`, `チョッキ` 같은 손으로 적은 별칭.
  일본 커뮤니티는 도구를 거의 줄여 쓰므로 정식 명칭만으로는 놓친다.

`リザードナイトＹ`처럼 전각 문자가 섞이므로 인덱스와 본문 양쪽을 NFKC로
정규화한다.

### 후보 집계

HTML을 의존성 없이 텍스트로 벗긴 뒤, 긴 이름부터 훑으며 찾은 자리를 덮어
`メガリザードンY`가 `リザードン`으로 잘려 두 번 세지 않게 한다. 이름마다 신호를
모은다.

1. 출현 횟수와 최초 위치
2. ±40자 내 도구 — `@`와 `持ち物` 표기, 약칭을 함께 본다
3. ±40자 내 부정 신호 — `見送り` `不採用` `候補` `相手` `過去`
4. `learnset`이 없는 종족은 강등 — 챔피언스 등장 371종 밖은 과거작 잡담이다
5. 메가 폼이 잡히면 도구를 그 메가스톤으로 채운다. 본문이 `メガルカリオ`라고만
   쓰고 `ルカリオナイト`를 안 써도 도구가 확정된다.

메가 폼과 기본 폼은 같은 자리이므로 기본 종족으로 묶어 점수를 합치고, 폼은 하위
항목으로 남긴다. 측정한 기사에서 `リザードン` 12회와 `メガリザードンY` 5회가
한 자리로 합쳐진다.

### 메타

`articles.json`의 필수 항목을 함께 뽑는다.

- 제목 — `og:title` 또는 `<title>`. 여기서 최종 순위, 시즌, 싱글/더블을 읽는다.
- 게시일 — `article:published_time`, 없으면 RSS의 날짜
- 작성자 — `og:site_name`은 블로그 이름이지 작성자가 아닌 경우가 많다(측정한
  기사에서 `人生詰みサイクル` 대 `rebo®`). 추정하지 않고 본문 첫 300자를
  `excerpt`로 넘겨 3단계가 읽게 한다.
- `id` — 기존 기록처럼 `<시즌 소문자>-<형식 소문자>-<작성자 슬러그>` 형태로
  제안한다. 최종 확정은 3단계에서 한다.

### 월간 챌린지 주의

검색 결과에 `【MCS 2026.08 最終670位】`, `【シーズンM-4最終44位・MCS26.07最終13位】`
같은 제목이 실제로 있었다. `docs/articles.md` 1번은 월간 챌린지 성적을 랭크배틀
최종 순위로 넣지 말라고 한다. 제목에 `MCS` 또는 `月間`이 있으면 `flags`에
`monthly-challenge`를 달아 3단계가 두 순위를 구분하게 한다.

`レギュM-B` 같은 레귤레이션 표기를 시즌으로 읽지 않도록, 시즌은 `シーズン` 뒤나
구분자 뒤의 `M-숫자` / `S숫자`만 받는다.

### 이미지

본문 `<img>`에서 아바타와 아이콘(`icon`, `avatar`, `profile`, `square`, `emoji`,
`badge`)을 걸러낸 뒤 등장 순서대로 최대 세 장을 캐시한다. 측정한 기사에서 첫
이미지는 블로그 아이콘이었고 실제 팀 이미지는 걸러낸 뒤 두 번째였다.

OCR은 하지 않는다. 3단계에서 AI가 직접 본다.

### 큐

기사 하나가 후보 8~12마리, 후보별 ±60자 발췌 최대 두 개, 메타와 `flags`를 담아
약 2KB가 된다. 후보가 여섯 미만이거나 제목에 최종 순위가 없어도 **버리지 않고**
`flags`를 달아 남긴다. 판단은 3단계 몫이다.

## 3단계 · 판정

Claude Code 세션이 큐와 캐시된 이미지를 읽고 최종 여섯 마리를 확정한 뒤
`teamEvidence`와 `rankEvidence`를 쓴다. 이미지 한 장은 1~1.5k 토큰으로,
`docs/articles.md` 2번 규칙인 본문과 이미지 대조를 원문 전문 없이 지킨다.

## 4단계 · 승격

`review.status`를 `pending`으로 두어 `articles.json`에 넣는다. `src/articles.js`의
`reviewedArticles`가 이미 `pending`을 거르므로 앱 코드는 바뀌지 않는다.
사람이 훑고 `reviewed`로 바꾸면 공개된다.

## 오류 처리

- 검색 피드가 실패하거나 구조가 바뀌면 그 어댑터만 건너뛰고 나머지를 계속한다.
  끝에 어댑터별 성공·실패 요약을 출력한다.
- 개별 URL의 fetch 실패는 건너뛰고 기록한다.
- 파싱이 애매한 기사는 `flags`를 달아 큐에 남긴다. 조용히 버리지 않는다.

## 테스트

- `tests/article-parse.test.mjs` — 검색으로 실제 수집한 제목과 짧은 본문 발췌를
  픽스처로 제목 파싱, 메가·리전 매칭, 도구 약칭, 부정 신호 강등, 월간 챌린지
  플래그를 검증한다.
- `tests/articles.test.mjs` — 현재 모든 항목이 공개 가능하다고 단언하므로,
  모든 항목의 형식 검증과 `reviewed` 항목만의 공개 검증으로 나눈다.

## 부수 수정

`scripts/update-reference.mjs`에서 `held_item`에 Showdown의 `megaStone` 값을
기록한다. 원본은 `{ "Gengar": "Gengar-Mega" }` 형태의 한 칸짜리 맵이고 93개
도구에 붙어 있다. 스톤에서 메가 폼을, 메가 폼에서 스톤을 정확히 얻기 위해서다.
한국어 설명문으로 대신할 수 없다. `뮤츠나이트X`와 `뮤츠나이트Y`의 설명문은
둘 다 폼을 밝히지 않는다.

## 하지 않는 것

- OCR — 이미지는 판정 단계에서 AI가 본다
- X(트위터) 수집 — 무료 경로가 없다
- 하테나 외 소스 어댑터 — 측정상 필요가 확인되지 않았다
- 서버, DB, 예약 실행 — 파서가 몇 시즌 안정된 뒤 GitHub Actions로 올린다
- 원문 텍스트와 이미지의 저장, 재배포 — 기존 방침 그대로다
