# 구축기사 수집 자동화 설계

`docs/articles.md`의 등록 기준은 그대로 두고, 그 기준을 만족하는 후보를 모아
사람 앞에 압축해 내놓는 도구를 만든다. 판정과 공개 결정은 여전히 사람 몫이다.

원문 전문을 AI 컨텍스트에 넣지 않는 것이 이 설계의 목적이다. 이름 읽기와 근거
수집은 로컬 데이터로 결정론적으로 처리하고, 비용을 쓸 가치가 있는 판단
— 이 여섯 마리가 **최종** 파티인가 — 에만 AI를 한 번 쓴다.

## 단계

| 단계 | 수행 주체 | 산출물 |
| --- | --- | --- |
| 1 수집 | `scripts/collect-articles.mjs` | 리드(기사 주소) → `.cache/articles/<sha1>.html` |
| 2 추출 | `scripts/article-parse.mjs` | `.cache/article-queue-<시즌>.json` (예: `article-queue-m5.json`) |
| 3 판정 | Claude Code 세션 | 최종 6마리와 근거문을 `pending`으로 기록 |
| 4 승격 | 사람 | `articles.json`의 `pending` → `reviewed` |

## 사전 측정

설계 중 실제 기사와 검색 피드로 다음을 확인했다. 숫자는 추정이 아니라 측정값이다.

- 하테나 북마크 검색 RSS 한 번에 40건이 돌아오고 그중 22건의 제목에 최종 순위가
  있었다. 나머지는 뉴스, 공략 사이트, 무관한 글이며 2단계 필터가 걸러낼 종류다.
- 그 40건에는 note, pokesol, fc2, seesaa, 개인 도메인 기사가 모두 섞여 있었다.
  **소스별 어댑터를 따로 만들 필요가 없다.**
- 기존 기록인 rebo 기사(`reboiona.hatenablog.com`)를 파싱하니 최종 6마리가 모두
  후보에 잡혔고 점수 상위 12위 안에 5마리가 들었다.
- 같은 기사에서 **도구는 6개 중 4개만 본문에 있었다.** 메가스톤 둘과
  `こだわりスカーフ`는 본문에 없고 작성자의 팀 이미지에만 있었다.
- 그 기사는 개별 해설에 `h2`/`h3`를 쓰지 않았다. **헤딩은 신뢰할 신호가 아니다.**

마지막 두 항목이 설계를 바꿨다. 텍스트만으로는 파티가 완성되지 않는다. 이미지가
판정의 중심이고, 압축 표는 이미지를 읽을 때 쓰는 대조표 역할을 한다.

## 1단계 · 수집

```
npm run articles -- --season M5 --format singles
npm run articles -- --season M5 --urls leads.txt --no-search
npm run articles -- --season M5 --from https://example.com/top-teams --no-search --no-feeds
```

`--season`은 필수다. `--format`을 생략하면 싱글과 더블을 모두 찾는다.

### 리드 채널 (2026-09-25 재설계)

첫 버전은 검색 두 곳(하테나 북마크, 구글)에만 기댔고 기사가 두 건에서 늘지 않았다.
원인은 셋이다.

- 하테나 북마크는 누군가 북마크한 글만 들어 있다. M-5 실측에서 300건 중 21건.
- 구글 Custom Search JSON API는 2025년에 새 가입을 닫았고, 새 검색 엔진은 전체 웹
  검색을 켤 수 없으며, API 자체가 2027-01-01에 끝난다. 사실상 새로 쓸 수 없다.
- 기사를 가장 잘 모아 둔 포케DB와 야쿤은 robots.txt로 AI 수집을 막는다.

그래서 **검색은 여러 리드 채널 중 하나**로 내리고, 기사 주소를 얻는 경로를 넷으로
나눴다. 채널마다 켜고 끌 수 있고, 어느 채널에서 왔는지는 큐의 `source`에 남는다.

| 채널 | 인자 | `source` | 제목 검사 |
| --- | --- | --- | --- |
| 주소 목록 | `--urls <파일>` (여러 번) | `manual` | 하지 않음 |
| 기사 모음 페이지 | `--from <주소>` (여러 번) | `index` | 하지 않음 |
| 작성자 피드 | 기본 켜짐, `--no-feeds` | `feed` | 함 |
| 검색 | 기본 켜짐, `--no-search` | `hatena`, `google` | 함 |

**주소 목록**이 가장 확실하다. 포케DB의 기사 목록, X, 디스코드처럼 이 도구가 받지
않는 곳에서 사람이 본 주소를 텍스트 파일에 한 줄씩 붙여 넣는다. 주소 뒤에 적은
글은 힌트로 읽는다. 제목에 순위가 없는 기사라도 `最終12位`를 적어 두면 순위가
채워지고 `rank-from-hint` 플래그가 붙는다. 브라우저로 저장한 목록 페이지 HTML을
넘겨도 된다. 그때는 기사처럼 보이는 링크만 쓴다.
무엇을 쓰고 무엇을 버렸는지는 `npm run leads -- leads\목록.html`로 본다(네트워크 없음).
버린 링크에 파티 기사가 있으면 추출 규칙을 고친다.

```
https://note.com/someone/n/n1234 最終12位
https://someone.hatenablog.com/entry/2026/09/10/000000
```

카드형 목록(포케DB처럼 순위는 윗줄, 기사 링크는 아랫줄)은 제목에 `最終`이 없으면
순위를 못 읽었다. 그래서 직전 기사 링크 뒤부터 이 링크 앞까지의 글에서 가장 가까운
`N位`를 `rankHint`로 따로 읽는다. 카드마다 기사 링크가 하나라 옆 카드의 순위가 넘어오지
않는다. 저장한 페이지의 원래 주소는 canonical, `og:url`, `saved from url` 주석에서 읽어
그 사이트 자체 링크를 버린다.

### 다른 게임 기사 거르기

작성자 피드와 검색은 같은 블로그의 지난 게임 기사를 섞어 온다. 첫 판정에서 상위 다섯 건이
모두 소드실드 S5, SV 시즌 20, 2022 竜王戦 기사였다. 제목의 `S5`는 시즌처럼 읽히므로
`gameCheck`가 게임을 따로 가린다.

- `before-champions`: 게시일이 M-1 시작(2026-04-08)보다 이르다
- `other-game`: 챔피언스 표기(チャンピオンズ, ポケチャン, M-5, レギュM 등)가 없고
  剣盾·SV·テラスタル·ダイマックス·竜王戦 같은 다른 게임 표기가 있다
- `no-champions-mention`: 어느 쪽 표기도 없다(플래그만)

검색·피드에서 온 기사는 앞의 둘이면 버리고(`other-game`으로 셈), 사람이 고른 주소는
챔피언스 목록에서 왔으므로 버리지 않고 플래그만 단다.

수집기는 돌 때마다 **이전 큐 전체를 캐시로 다시 판단**한다. 규칙을 고친 뒤 한 번 돌리면
이미 쌓인 오탐도 빠진다. 큐는 사람이 고른 주소를 앞에, 그 안에서 순위순으로 정렬한다.

### 사람 검토 목록

수집기가 받지 않는 기사는 판정 큐 대신 `leads/review-<시즌>.txt`에 남는다. 한 줄에
`순위 · 이유 · 주소 · 제목`을 탭으로 나눠 적고, 다시 돌려도 같은 주소는 한 번만 적는다.
사람이 원문을 보고 여섯 마리와 도구를 확인해 `articles.json`에 직접 넣을 목록이다.

| 이유 | 대상 |
| --- | --- |
| 수집 금지 호스트 | 네이버 블로그·카페, 포케DB (`isFetchable`) |
| robots.txt | robots.txt가 AI 에이전트를 막은 곳 (야쿤 등) |
| X 게시물 | `x.com`·`twitter.com`의 `/status/` 주소. 로그인 없이는 본문이 나오지 않는다 |
| YouTube 영상 | `watch`, `youtu.be`, `shorts`, `live` 주소. 팀이 영상 속에만 있어 대조할 수 없다 |
| 받기 실패 | 받지 못한 주소. 다시 돌려도 안 되면 사람이 본다 |

X의 계정 프로필, 유튜브 채널·재생목록, 디스코드 링크는 기사가 아니어서 리드로 쓰지 않는다.

**기사 모음 페이지**는 공략 사이트의 상위 구축 모음처럼 원문 링크를 모아 둔 곳이다.
링크만 거두고 그 페이지의 본문은 큐에 넣지 않는다. 같은 사이트 안의 링크(메뉴, 다른
공략)는 버리고, 알려진 블로그 기사 주소이거나 같은 표 행·목록 항목에 최종 순위가
적힌 링크만 남긴다. 페이지 자체도 robots.txt를 확인한다.

**작성자 피드**는 상위 랭커가 시즌마다 같은 블로그에 쓴다는 점을 쓴다.
`articles.json`에 등록했거나 큐에 올랐던 기사의 주소에서 블로그 피드를 되짚는다.
주소만으로 피드가 정해지는 서비스만 다룬다.

| 서비스 | 피드 |
| --- | --- |
| 하테나 블로그 | `<블로그>/feed` |
| note | `https://note.com/<작성자>/rss` |
| 아메바 블로그 | `https://rssblog.ameba.jp/<작성자>/rss20.xml` |
| FC2 | `<블로그>/?xml` |
| 라이브도어, seesaa | `<블로그>/index.rdf` |

pokesol은 공개된 작성자 피드를 찾지 못했다. 그 외에 따로 볼 피드나 기사 주소는
`scripts/article-feeds.json`의 `feeds`에 적는다. 기사 주소를 적으면 피드로 바꿔 본다.
피드에는 지난 시즌 기사도 있으므로 제목의 시즌이 다르면 받기 전에 버린다.

큐는 시즌마다 파일을 나눈다(`article-queue-m5.json`). 한 파일에 두면 지난 시즌 후보가
이번 판정에 섞인다. 작성자 피드는 시즌과 무관하므로 모든 시즌의 큐와 옛 이름
`article-queue.json`에서 되짚는다. 같은 시즌 큐는 **합친다**. 검색 한 번, 주소 목록 한 번처럼 나눠 돌려도 앞의 결과가
지워지지 않는다. 다시 본 주소는 새 결과로 바꾸고, 그사이 `articles.json`에 등록된
주소는 뺀다.

### 검색어

게임명 상수 네 개를 순위 표현과 조합한다.

- `ポケモンチャンピオンズ`
- `ポケモン チャンピオンズ`
- `ポケチャン`
- `チャンピオンズ`

앞의 두 개는 공백만 다르다. 하테나는 공백을 AND 검색으로 쪼개므로, 형태소
분석기가 복합어를 알아서 나누면 결과가 같고 아니면 다르다. 확인하는 비용보다
둘 다 넣는 비용이 싸다. URL 중복 제거가 겹치는 결과를 걷어낸다.

여기에 `最終`과 시즌 표기를 붙인다. 시즌은 `--season` 인자를 `M-5` / `S5` 두
표기로 펼친다. 측정에서 `S5` 쪽이 `M-5`보다 훨씬 많이 걸렸다.

**형식은 검색어에 넣지 않는다.** `シングル`을 더하는 것만으로 하테나의 AND
검색이 고유 URL을 44건에서 5건으로 깎았다. 구축기사 제목이 형식을 밝히지 않는
경우가 흔하기 때문이다. 형식은 받아온 뒤 제목으로 거른다.

`チャンピオンズ`만 쓰면 **경마**가 딸려 온다. `チャンピオンズカップ`가 중상
경주 이름이고 `最終予想`이 예상 글의 관용구라, 측정한 회차에서 44건 중 35건이
경마 글이었다. 그래서 받아오기 전에 제목을 본다. 제목에 `最終 N 位`나
`ポケモン` / `ポケチャン` / `構築`이 없으면 요청하지 않는다. 받아오고 나서
거르면 요청과 시간만 버린다.

블로그 첫 페이지도 걸러낸다. 포켓몬 이름이 잔뜩 있어 후보 수 검사를 통과해
버리므로 주소의 경로가 비어 있으면 기사가 아닌 것으로 본다.

### 받아오지 않는 곳

`robots.txt`로 AI 목적 수집을 금지한 사이트는 받지 않는다. 목록 페이지와 작성자
피드로 처음 보는 호스트가 계속 들어오므로, 알려진 곳을 적어 둔 `isFetchable`에 더해
**호스트마다 robots.txt를 받아** `robotsAllows`로 판정한다(RFC 9309: 이름이 맞는
묶음 우선, 가장 긴 규칙 우선, 같으면 Allow).

판정에 쓰는 에이전트는 우리 User-Agent, `ClaudeBot`, `Claude-User`,
`Claude-SearchBot`, `ChatGPT-User`, `Perplexity-User`다. 하나라도 막히면 받지 않는다.
수집한 본문을 3단계에서 AI가 읽기 때문이다. `GPTBot`, `Google-Extended`처럼 학습
전용 표기만 막은 곳은 이 용도와 무관해 보지 않는다. robots.txt가 4xx면 파일이 없는
것으로 보고 허용하고, 5xx나 시간 초과로 읽지 못하면 받지 않는다.

| 호스트 | robots.txt |
| --- | --- |
| `champs.pokedb.tokyo` | `ClaudeBot`, `Claude-SearchBot`에 `Disallow: /` |
| `blog.naver.com`, `m.blog.naver.com` | RAG 목적 수집 금지를 명시하고 `ClaudeBot` 지정 |
| `cafe.naver.com` | `User-agent: *`에 `Disallow: /` |

User-Agent를 바꾸면 기술적으로는 받아진다. 하지 않는다. 사이트가 AI에게 주지
않겠다고 밝힌 것을 이름만 바꿔 가져오는 것이기 때문이다.

이 때문에 **네이버 검색 오픈 API는 쓰지 않는다.** 검색 API 자체는 열려 있지만
돌려주는 것은 주소와 두어 줄 요약뿐이고, 여섯 마리를 뽑으려면 본문이 필요한데
본문 수집이 금지되어 있다. 포케DB 목록도 마찬가지로, 쓰려면 사람이 직접 보고
주소를 넘기는 수밖에 없다.

`note.com`은 `/search`와 `/api/*`를 모두에게 막는다. 검색은 못 쓰지만 개별
기사 주소는 받아도 된다. `yakkun.com`은 `ChatGPT-User`를 막는다. Claude를
지목하지는 않았으나 사용자 요청형 에이전트를 막은 곳이라 쓰지 않는다.

### 검색 채널

**구글 Custom Search JSON API** — 2027-01-01에 끝나고 새 가입이 닫혀 있다. 이미 키와
전체 웹 검색 엔진이 있는 경우만 쓴다. `GOOGLE_API_KEY`와 `GOOGLE_CSE_ID` 환경변수가
있을 때만 돌고, 없으면 이 채널만 건너뛴다. 무료 한도가 하루 100건이라 쿼리당 두
쪽(20건)까지만 본다.

- 키: Google Cloud Console에서 **Custom Search API**를 켜고 API 키를 만든다
- 엔진 ID: Programmable Search Engine에서 엔진을 만들고 **전체 웹 검색**을 켠 뒤
  Search engine ID를 복사한다

```powershell
$env:GOOGLE_API_KEY = "..."
$env:GOOGLE_CSE_ID = "..."
npm run articles -- --season M5 --format singles
```

**하테나 북마크 검색 RSS** — 키가 필요 없다.

```
https://b.hatena.ne.jp/q/<검색어>?mode=rss&target=text&users=1&sort=recent
```

`users` 기본값이 3이라 그대로 두면 북마크 3개 미만인 개인 구축기사가 거의 전부
빠진다. 측정에서 40건과 4건으로 갈렸으므로 `users=1`을 반드시 붙인다.
`/search/text` 경로는 이 주소로 301 이동한다.

누군가 북마크한 글만 들어 있어 재현율이 낮다. M-5 실측에서 목록에 300건이 있는데
21건만 보였다. 구글 채널이 이것을 메운다.

X(트위터)는 무료 경로가 없어 제외한다.

### 요청 규칙

원문은 `.cache/articles/<sha1>.html`에 캐시하고 캐시가 있으면 다시 받지 않는다.
요청 간 1초 간격을 두고 User-Agent에 이 저장소를 밝힌다. `articles.json`에 이미
있는 URL은 건너뛴다. `.cache/`는 gitignore이므로 원문 텍스트와 이미지는 커밋에
들어가지 않는다. 커밋되는 것은 추출된 사실뿐이다.

## 2단계 · 추출

`scripts/article-parse.mjs`는 네트워크를 쓰지 않는 순수 함수만 내보낸다.
고정 픽스처로 테스트하고, 파서를 고칠 때 원문을 다시 긁지 않기 위해서다.

### 일본어 인덱스

`reference.json`과 `ko.json`에서 빌드한다.

- 기본 종족 1024건 — `ko.json`의 `japanese.pokemon`
- 메가 폼 — `メガ` + 기본명 + `forme`의 꼬리(`X` / `Y` / `Z`). 니야오닉스처럼
  폼이 나뉜 종족은 `forme`이 `M-Mega` 꼴이라 꼬리를 붙이지 않고 `メガ` + 기본명만
  만든다. 어차피 기본 종족으로 묶어 세므로 후보를 놓치지 않는다.
- 리전 폼 — `アローラ` / `ガラル` / `ヒスイ` / `パルデア` + 기본명
- 도구 431건 — `reference.json`의 `held_item[].japanese`
- 도구 약칭 — `スカーフ`, `タスキ`, `ゴツメ`, `チョッキ` 같은 손으로 적은 별칭.
  일본 커뮤니티는 도구를 거의 줄여 쓰므로 정식 명칭만으로는 놓친다.

`リザードナイトＹ`처럼 전각 문자가 섞이므로 인덱스와 본문 양쪽을 NFKC로
정규화한다.

### 후보 집계

HTML을 의존성 없이 텍스트로 벗긴 뒤, 긴 이름부터 훑으며 찾은 자리를 덮어
`メガリザードンY`가 `リザードン`으로 잘려 두 번 세지 않게 한다. 이름마다 신호를
모은다.

1. 출현 횟수와 최초 위치
2. ±40자 내 도구 — `@`와 `持ち物` 표기, 약칭을 함께 본다
3. ±40자 내 부정 신호 — `見送り` `不採用` `候補` `相手` `過去`
4. `learnset`이 없는 종족은 강등 — 챔피언스 등장 371종 밖은 과거작 잡담이다
5. 메가 폼이 잡히면 도구를 그 메가스톤으로 채운다. 본문이 `メガルカリオ`라고만
   쓰고 `ルカリオナイト`를 안 써도 도구가 확정된다.

메가 폼과 기본 폼은 같은 자리이므로 기본 종족으로 묶어 점수를 합치고, 폼은 하위
항목으로 남긴다. 측정한 기사에서 `リザードン` 12회와 `メガリザードンY` 5회가
한 자리로 합쳐진다.

### 메타

`articles.json`의 필수 항목을 함께 뽑는다.

- 제목 — `og:title` 또는 `<title>`. 여기서 최종 순위, 시즌, 싱글/더블을 읽는다.
- 게시일 — `article:published_time`, 없으면 RSS의 날짜
- 작성자 — `og:site_name`은 블로그 이름이지 작성자가 아닌 경우가 많다(측정한
  기사에서 `人生詰みサイクル` 대 `rebo®`). 추정하지 않고 본문 첫 300자를
  `excerpt`로 넘겨 3단계가 읽게 한다.
- `id` — 기존 기록처럼 `<시즌 소문자>-<형식 소문자>-<작성자 슬러그>` 형태로
  제안한다. 최종 확정은 3단계에서 한다.

### 월간 챌린지 주의

검색 결과에 `【MCS 2026.08 最終670位】`, `【シーズンM-4最終44位・MCS26.07最終13位】`
같은 제목이 실제로 있었다. `docs/articles.md` 1번은 월간 챌린지 성적을 랭크배틀
최종 순위로 넣지 말라고 한다. 제목에 `MCS` 또는 `月間`이 있으면 `flags`에
`monthly-challenge`를 달아 3단계가 두 순위를 구분하게 한다.

`レギュM-B` 같은 레귤레이션 표기를 시즌으로 읽지 않도록, 시즌은 `シーズン` 뒤나
구분자 뒤의 `M-숫자` / `S숫자`만 받는다.

### 이미지

본문 `<img>`에서 아바타와 아이콘(`icon`, `avatar`, `profile`, `square`, `emoji`,
`badge`)을 걸러낸 뒤 등장 순서대로 최대 세 장을 캐시한다. 측정한 기사에서 첫
이미지는 블로그 아이콘이었고 실제 팀 이미지는 걸러낸 뒤 두 번째였다.

OCR은 하지 않는다. 3단계에서 AI가 직접 본다.

### 큐

기사 하나가 후보 최대 16마리, 후보별 ±50자 발췌 하나, 메타와 `flags`를 담아 약
4KB가 된다. 상한이 16인 것은 측정 때문이다. 12로 두면 실제 멤버인 ミミッキュ가
떨어지고 상대 포켓몬인 カバルドン이 남았다. 본문 등장 횟수와 도구 근접만으로는
둘을 가를 수 없으므로, 점수를 손보는 대신 그물을 넓혀 멤버를 떨어뜨리지 않는
쪽을 택했다. 가려내는 일은 이미지를 보는 3단계가 한다.

점수는 본문에서 실제로 찾은 도구로만 매긴다. 폼에서 되짚은 메가스톤까지 세면
구축 경위에 환경 상위 메가로 이름만 오른 포켓몬이 실제 멤버를 밀어낸다.

후보가 여섯 미만이거나 제목에 최종 순위가 없어도 **버리지 않고** `flags`를 달아
남긴다. 판단은 3단계 몫이다.

## 3단계 · 판정

절차는 [article-judging.md](article-judging.md)에 있다. 수집기가 본문 이미지(최대 세 장)를
`.cache/articles/`에 받아 두고 큐의 `imageFiles`에 적는다. 파티 기사가 아니라고 판정한
주소는 `scripts/article-skip.json`에 넣어 다시 큐에 올리지 않는다.

Claude Code 세션이 큐와 캐시된 이미지를 읽고 최종 여섯 마리를 확정한 뒤
`teamEvidence`와 `rankEvidence`를 쓴다. 이미지 한 장은 1~1.5k 토큰으로,
`docs/articles.md` 2번 규칙인 본문과 이미지 대조를 원문 전문 없이 지킨다.

## 4단계 · 승격

`review.status`를 `pending`으로 두어 `articles.json`에 넣는다. `src/articles.js`의
`reviewedArticles`가 이미 `pending`을 거르므로 앱 코드는 바뀌지 않는다.
사람이 훑고 `reviewed`로 바꾸면 공개된다.

## 오류 처리

- 검색 피드가 실패하거나 구조가 바뀌면 그 검색만 건너뛰고 나머지를 계속한다.
- 개별 URL의 fetch 실패는 건너뛰고 기록한다.
- 파싱이 애매한 기사는 `flags`를 달아 큐에 남긴다. 조용히 버리지 않는다.
- 끝에 왜 걸렀는지를 이유별로 센 요약을 출력한다. 한 건도 안 남았을 때 검색어
  탓인지 필터 탓인지 알아야 하기 때문이다.

## 실행 결과

M-3 싱글로 돌린 결과다.

- 검색 8회 → 제목 검사를 통과한 후보 21건 → 큐 15건, 71KB(건당 약 4.8KB)
- 15건 모두 제목에서 시즌과 최종 순위가 읽혔다
- 11건에 `format-missing`이 붙었다. 제목이 싱글·더블을 밝히는 경우가 오히려
  드물다. 3단계가 본문으로 판단한다

M-5로 돌리면 한 건도 안 나온다. 시즌이 끝난 지 얼마 안 되어 북마크된 기사가
아직 없어서다. 검색이 도는 데는 문제가 없으며 시즌이 무르익으면 채워진다.

## 부수 수정

`scripts/update-reference.mjs`에서 `held_item`에 Showdown의 `megaStone` 값을
기록한다. 원본은 `{ "Gengar": "Gengar-Mega" }` 형태의 한 칸짜리 맵이고 93개
도구에 붙어 있다. 스톤에서 메가 폼을, 메가 폼에서 스톤을 정확히 얻기 위해서다.
한국어 설명문으로 대신할 수 없다. `뮤츠나이트X`와 `뮤츠나이트Y`의 설명문은
둘 다 폼을 밝히지 않는다.

## 하지 않는 것

- 포케DB, 야쿤, 네이버 목록의 자동 수집 — robots.txt가 막는다. 사람이 본 주소를
  `--urls`로 넘기는 것만 받는다
- 유료 검색 API 대체(Brave, SerpAPI 등) — 채널을 더하기는 쉽지만 키 관리 비용이 있다.
  주소 목록과 작성자 피드로 부족할 때 다시 본다
- OCR — 이미지는 판정 단계에서 AI가 본다
- X(트위터) 수집 — 무료 경로가 없다
- 사이트별 본문 어댑터 — 측정상 필요가 확인되지 않았다. 리드 채널만 늘렸다
- 서버, DB, 예약 실행 — 파서가 몇 시즌 안정된 뒤 GitHub Actions로 올린다
- 원문 텍스트와 이미지의 저장, 재배포 — 기존 방침 그대로다
