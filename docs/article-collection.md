# 구축기사 수집 자동화 설계

`docs/articles.md`의 등록 기준은 그대로 두고, 그 기준을 만족하는 후보를 모아
사람 앞에 압축해 내놓는 도구를 만든다. 판정과 공개 결정은 여전히 사람 몫이다.

원문 전문을 AI 컨텍스트에 넣지 않는 것이 이 설계의 목적이다. 이름 읽기와 근거
수집은 로컬 데이터로 결정론적으로 처리하고, 비용을 쓸 가치가 있는 판단
— 이 여섯 마리가 **최종** 파티인가 — 에만 AI를 한 번 쓴다.

## 단계

| 단계 | 수행 주체 | 산출물 |
| --- | --- | --- |
| 1 수집 | `scripts/collect-articles.mjs` | `.cache/articles/<sha1>.html`, 이미지 |
| 2 추출 | `scripts/article-parse.mjs` | `.cache/article-queue.json` (기사당 약 1.5KB) |
| 3 판정 | Claude Code 세션 | 최종 6마리와 근거문을 `pending`으로 기록 |
| 4 승격 | 사람 | `articles.json`의 `pending` → `reviewed` 승격 |

## 1단계 · 수집

`npm run articles -- --season M5 --format singles`

`--season`은 필수다. `--format`을 생략하면 싱글과 더블을 모두 찾는다.

### 검색어

게임명 상수 세 개를 순위 표현과 조합한다.

- `ポケモン チャンピオンズ`
- `ポケチャン`
- `チャンピオンズ`

세 번째는 포켓몬 외 결과가 섞일 수 있으나, 2단계의 챔피언스 종족 필터와 제목
순위 파싱이 걸러낸다. 순위 표현은 `最終` + 순위, 형식은 `シングル` / `ダブル`,
시즌은 `--season` 인자를 `M-5` / `S5` 두 표기로 펼쳐 붙인다.

### 소스 어댑터

`{ name, searchUrl(query), extractLinks(body) }` 세 필드짜리 객체로 시작 세 개를
둔다. API 키가 필요 없는 경로만 쓴다.

- 하테나 북마크 검색 RSS — `b.hatena.ne.jp/search/text?q=…&mode=rss`
- note 검색 JSON — `note.com/api/v3/searchs?context=note&q=…`
- pokesol 목록

X(트위터)는 무료 경로가 없어 제외한다. 구축기사는 대부분 블로그와 기사
플랫폼에 올라오고 X에는 링크만 도는 경우가 많다. 어댑터 추가 비용이 낮으므로
빠진 소스는 나중에 붙인다.

### 요청 규칙

원문은 `.cache/articles/<sha1>.html`에 캐시하고 캐시가 있으면 다시 받지 않는다.
요청 간 1초 간격을 두고 User-Agent에 이 저장소를 밝힌다. `articles.json`에 이미
있는 URL은 건너뛴다. `.cache/`는 gitignore이므로 원문 텍스트와 이미지는 커밋에
들어가지 않는다. 커밋되는 것은 추출된 사실뿐이다.

## 2단계 · 추출

`scripts/article-parse.mjs`는 네트워크를 쓰지 않는 순수 함수만 내보낸다.
고정 픽스처로 테스트하고, 파서를 고칠 때 원문을 다시 긁지 않기 위해서다.

### 일본어 인덱스

`reference.json`과 `ko.json`에서 빌드한다.

- 기본 종족 1024건 — `ko.json`의 `japanese.pokemon`
- 메가 폼 — `メガ` + 기본명. `species.megas`에 있는 폼만 만든다.
- 리전 폼 — `アローラ` / `ガラル` / `ヒスイ` / `パルデア` + 기본명.
  `species.forme`가 그 지역인 폼만 만든다.
- 도구 431건 — `reference.json`의 `held_item[].japanese`

`リザードナイトＹ`처럼 전각 `Ｘ` / `Ｙ`가 섞이므로 인덱스와 본문 양쪽을
정규화한다.

### 후보 집계

HTML을 의존성 없이 텍스트로 벗긴 뒤, 인덱스에 걸린 이름마다 신호를 모은다.

1. 출현 횟수와 최초 위치
2. 헤딩(`h2` / `h3`) 등장 여부 — 개별 해설이 있다는 강한 신호
3. ±40자 내 도구 — `@`와 `持ち物` 표기를 함께 본다
4. ±40자 내 부정 신호 — `見送り` `不採用` `候補` `相手` `過去`
5. `learnset`이 없는 종족은 강등 — 챔피언스 등장 371종 밖은 과거작 잡담일 확률이 높다
6. 메가스톤이 잡히면 메가 폼을 확정한다

### 메타

`articles.json`의 필수 항목을 함께 뽑는다.

- 제목 — `<title>` 또는 `og:title`. 여기서 최종 순위, 시즌, 싱글/더블 표기를
  읽는다.
- 작성자 — 소스 어댑터가 검색 결과에서 준 값을 우선하고, 없으면 `og:site_name`
  이나 본문 서명에서 찾는다. 못 찾으면 비워 두고 `flags`에 남긴다.
- 게시일 — `article:published_time`, RSS의 날짜, pokesol JSON 순으로 본다.
- `id` — 기존 기록처럼 `<시즌 소문자>-<형식 소문자>-<작성자 슬러그>` 형태로
  제안한다. 충돌하면 끝에 숫자를 붙인다. 최종 확정은 3단계에서 한다.

본문 영역의 `<img>`를 등장 순서대로 최대 세 장 캐시한다. OCR은 하지 않는다.
3단계에서 AI가 직접 본다.

### 큐

기사 하나가 후보 8~12마리와 각각의 근거 발췌를 담아 약 1.5KB가 된다.
후보가 여섯 미만이거나 제목에 최종 순위가 없어도 **버리지 않고** `flags`를 달아
남긴다. 판단은 3단계 몫이다.

## 3단계 · 판정

Claude Code 세션이 큐와 캐시된 팀 이미지를 읽고 최종 여섯 마리를 확정한 뒤
`teamEvidence`와 `rankEvidence`를 쓴다. 이미지 한 장은 1~1.5k 토큰으로,
`docs/articles.md` 2번 규칙인 본문과 이미지 대조를 원문 전문 없이 지킨다.

## 4단계 · 반영

`review.status`를 `pending`으로 두어 `articles.json`에 넣는다. `src/articles.js`의
`reviewedArticles`가 이미 `pending`을 거르므로 앱 코드는 바뀌지 않는다.
사람이 훑고 `reviewed`로 바꾸면 공개된다.

## 오류 처리

- 검색 피드가 실패하거나 구조가 바뀌면 그 어댑터만 건너뛰고 나머지를 계속한다.
  끝에 어댑터별 성공/실패 요약을 출력한다.
- 개별 URL의 fetch 실패는 건너뛰고 기록한다.
- 파싱이 애매한 기사는 `flags`를 달아 큐에 남긴다. 조용히 버리지 않는다.

## 테스트

- `tests/article-parse.test.mjs` — 기존 두 기사에서 뽑은 짧은 발췌를 픽스처로
  제목 파싱, 메가·리전 매칭, 도구 페어링, 부정 신호 강등을 검증한다.
- `tests/articles.test.mjs` — 현재 모든 항목이 공개 가능하다고 단언하므로,
  모든 항목의 형식 검증과 `reviewed` 항목만의 공개 검증으로 나눈다.

## 부수 수정

`scripts/update-reference.mjs`에서 `held_item`에 Showdown의 `megaStone` 값을
기록한다. 스톤에서 메가 폼을 추측 대신 정확히 얻기 위해서다.

## 하지 않는 것

- OCR — 이미지는 판정 단계에서 AI가 본다
- X(트위터) 수집 — 무료 경로가 없다
- 서버, DB, 예약 실행 — 파서가 몇 시즌 안정된 뒤 GitHub Actions로 올린다
- 원문 텍스트와 이미지의 저장, 재배포 — 기존 방침 그대로다
